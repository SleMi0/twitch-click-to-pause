# AGENTS.md — Twitch Click to Pause

## 1. Назначение проекта

Ты работаешь над **Twitch Click to Pause** — минималистичным расширением Chrome на Manifest V3.

Репозиторий: https://github.com/SleMi0/twitch-click-to-pause

Основная задача расширения — управление воспроизведением Twitch кликом непосредственно по области видео:

- Один клик — пауза или возобновление воспроизведения.
- Двойной клик — переключение полноэкранного режима без нежелательной паузы.
- Поддержка Live, VOD и Clips.
- Поддержка встроенных Twitch-плееров.
- Поддержка сторонних Twitch Extensions и их cross-origin iframe.
- Корректная работа при SPA-переходах между каналами.
- Отсутствие вмешательства в штатные элементы управления Twitch.

Твоя главная задача — развивать проект, сохраняя его простоту, предсказуемость, надёжность и совместимость с Twitch.

## 2. Приоритеты разработки

Соблюдай следующий порядок приоритетов:

1. Корректность поведения расширения.
2. Отсутствие регрессий существующих функций.
3. Совместимость с различными вариантами Twitch-плеера.
4. Безопасность взаимодействия между документами и iframe.
5. Минимальное вмешательство в работу Twitch.
6. Простота реализации и сопровождаемость.
7. Производительность.
8. Минимальный размер расширения и отсутствие ненужных зависимостей.

Не усложняй архитектуру без объективной необходимости.

Не добавляй функциональность, которая не требуется для решения поставленной задачи.

## 4. Архитектурные инварианты

Любые изменения должны сохранять следующие свойства.

### 4.1. Обработка кликов

- Обработчики событий должны корректно работать в capture phase.
- Необходимо предотвращать повторную обработку одного пользовательского действия Twitch и самим расширением.
- Синтетические клики, создаваемые расширением, не должны восприниматься как новые пользовательские клики.
- Один клик и двойной клик должны корректно различаться.
- Отложенное переключение воспроизведения не должно создавать нежелательные побочные эффекты.
- Новые пользовательские действия должны иметь приоритет над устаревшими отложенными операциями.

### 4.2. Управление воспроизведением

Приоритет отдавай нативной кнопке Twitch:

`button[data-a-target="player-play-pause-button"]`

Использование `video.play()` и `video.pause()` допустимо как fallback, когда штатная кнопка недоступна.

Не заменяй существующий механизм управления воспроизведением без проверки следующих сценариев:

- Live.
- VOD.
- Clips.
- Переподключение Live-трансляции.
- Перерисовка плеера.
- Переход между каналами.
- Несколько видеоплееров на странице.

Особое внимание уделяй синхронизации фактического состояния видео и внутреннего состояния Twitch-плеера.

### 4.3. Двойной клик и Fullscreen

Двойной клик должен:

- Переключать полноэкранный режим.
- Не вызывать нежелательную паузу.
- Не оставлять видео в неправильном состоянии воспроизведения.
- Не вмешиваться в полноэкранный режим другого элемента страницы.
- Корректно обрабатывать отказ Fullscreen API.

Не удаляй механизмы восстановления состояния воспроизведения без доказательства их ненужности.

### 4.4. Определение области видео

При обработке клика учитывай:

- Реальные координаты события.
- Размеры и видимость video.
- Наличие нескольких video.
- Перекрывающие элементы.
- DOM-структуру Twitch Player.
- Модальные окна.
- Большую кнопку Play поверх остановленного видео.

Не считай любое попадание в прямоугольник видео достаточным основанием для переключения воспроизведения.

### 4.5. Игнорирование интерактивных элементов

Необходимо сохранять штатную работу:

- Кнопок.
- Ссылок.
- Полей ввода.
- Настроек.
- Меню.
- Чата.
- Seekbar.
- Элементов управления воспроизведением.
- Контролов громкости.
- Интерактивных элементов сторонних Twitch Extensions.

Не расширяй и не сокращай IGNORE_SELECTOR без анализа возможных побочных эффектов.

Большая кнопка Play, перекрывающая область видео, является исключением: она должна восприниматься как поверхность плеера.

### 4.6. Twitch Extensions и iframe

Поддержка cross-origin iframe является важной частью проекта.

При изменениях необходимо сохранять:

- Обнаружение iframe с доменом ext-twitch.tv.
- Передачу координат клика родительскому документу.
- Корректное преобразование координат между iframe.
- Поддержку вложенных iframe.
- Предотвращение повторной обработки пересланных событий.
- Проверку фактического расположения клика относительно видео.
- Игнорирование интерактивных элементов самого расширения.

Особенно внимательно проверяй изменения, связанные с postMessage.

Не считай сообщение доверенным только потому, что оно содержит ожидаемый type.

Проверяй источник сообщения, соответствие iframe, допустимые данные, координаты и механизм дедупликации.

Не ослабляй существующие проверки безопасности ради упрощения кода.

### 4.7. SPA-навигация

Twitch — SPA-приложение.

Не предполагай, что переход между каналами приводит к полной перезагрузке документа.

Проверяй:

- Сохранение работоспособности обработчиков.
- Замену DOM-элементов плеера.
- Появление нового video.
- Удаление старого video.
- Переключение между разными типами плееров.

Избегай повторной установки глобальных обработчиков при повторной инициализации.

## 9. Правила работы с кодом

### 9.1. Стиль

- Используй современный Vanilla JavaScript.
- Предпочитай const.
- Используй let только при необходимости изменения значения.
- Сохраняй существующий стиль форматирования.
- Используй понятные имена переменных и функций.
- Избегай чрезмерной вложенности.
- Не создавай абстракции без практической необходимости.
- Не дублируй существующую логику.
- Комментируй сложные участки, объясняя причину решения.

### 9.2. Работа с состоянием

Особое внимание уделяй:

- pendingClick.
- playbackRestoreToken.
- clickingNativeButton.
- seenForwardedClicks.
- Таймерам и их очистке.

При изменении состояния проверяй:

- Возможность устаревших callback.
- Гонки между событиями.
- Повторное выполнение операций.
- Корректную отмену отложенных действий.
- Очистку временных данных.

Не удаляй защитные механизмы без анализа всех связанных сценариев.

### 9.3. DOM

- Не предполагай, что элементы Twitch всегда существуют.
- Проверяй доступность элементов перед использованием.
- Учитывай динамическое изменение DOM.
- Не привязывай реализацию к одному CSS-классу без необходимости.
- По возможности используй стабильные data-a-target.
- Не выполняй глобальный поиск элементов, если можно ограничить область поиска текущим плеером.

### 9.4. Ошибки

- Не допускай необработанных Promise rejection.
- Учитывай возможные ошибки Fullscreen API.
- Не допускай ошибок при удалении DOM-элементов.
- Не ломай воспроизведение из-за необязательных операций.
- Не скрывай ошибки, которые свидетельствуют о реальной проблеме.

## 10. Работа с manifest.json

Manifest V3 является обязательным.

При его изменении:

- Проверяй JSON-синтаксис.
- Проверяй matches.
- Проверяй run_at.
- Проверяй all_frames.
- Проверяй пути к файлам.
- Проверяй permissions и host_permissions.
- Не добавляй разрешения без необходимости.
- Проверяй совместимость с Chrome Extension Manifest V3.

Текущие важные настройки:

- manifest_version: 3.
- run_at: document_start.
- all_frames: true.
- content script: src/content.js.
- Twitch-домены и домены Twitch Extensions.

## 11. Документация

При изменении пользовательского поведения обновляй:

- README.md.
- README.en.md.

Обе версии должны описывать одинаковую функциональность.

Не документируй неподтверждённые возможности.

Если изменились ограничения, алгоритм работы или установка, обнови соответствующие разделы.

Комментарии в исходном коде должны отражать реальное поведение реализации.

## 12. Работа с Git

- Не изменяй чужие незакоммиченные изменения.
- Не выполняй destructive-команды без необходимости.
- Не используй git reset --hard.
- Не удаляй пользовательские файлы.
- Не создавай коммиты без соответствующего запроса или согласованного рабочего процесса.
- Не переписывай историю Git без прямого разрешения.
- Проверяй git diff перед завершением.

Коммиты, если они требуются, должны содержать логически связанные изменения.

## 13. Управление scope

Всегда придерживайся поставленной задачи.

Не выполняй автоматически:

- Масштабный рефакторинг.
- Переименование большого количества функций.
- Изменение структуры проекта.
- Добавление новых зависимостей.
- Изменение архитектуры.
- Изменение пользовательского поведения за пределами задачи.

Если в процессе обнаружена дополнительная проблема:

1. Определи её влияние.
2. Проверь, связана ли она с текущей задачей.
3. Сообщи о ней.
4. Не расширяй scope без необходимости.

## 14. Формат итогового отчёта

После выполнения задачи предоставляй отчёт:

### Что сделано
Краткое описание реализованных изменений.

### Какие файлы изменены
Список файлов и назначение изменений.

### Проверки
Для каждой проверки указывай:

- Название.
- Команду или способ выполнения.
- Фактический результат.

### Регрессии
Какие потенциальные регрессии проверены и какие остались непроверенными.

### Ограничения
Что невозможно было проверить и почему.

### Итог
Чёткий вывод о готовности задачи.

Не используй формулировки «всё работает», «полностью протестировано» и «ошибок нет» без достаточных подтверждений.

## 15. Главный принцип

**Сохраняй работающую функциональность, исправляй первопричины, проверяй каждое существенное изменение и не усложняй проект без необходимости.**

Главный критерий качества — не количество написанного кода, а доказуемая корректность поведения расширения в реальных сценариях Twitch.
